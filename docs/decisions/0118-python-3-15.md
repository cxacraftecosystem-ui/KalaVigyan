# 0118. The backend runs on Python 3.15, and each release pins its interpreter

The backend, the tools and the craft ETL require Python 3.15, in CI and on the box. The box's
interpreter is named by each release in `infra/deploy/python.pin` and installed by the release
beside every older one, so it moves without a rebuild and a rollback keeps each release on the
interpreter it was built with. The geo ETL stays on 3.14 until `exactextract` publishes a cp315
wheel.

Date: 2026-11-21. Status: accepted (owner, 2026-11-21, on whether to move to Python 3.15: "if it is
upgradable, upgrade it."). The guard is `backend/tests/test_python_version.py`.

## Context

The backend, the tools and the craft ETL required Python 3.14. CI set 3.14 in each workflow, and
the box ran every release on CPython 3.14.10 from python-build-standalone 20261110, installed once
into `/opt/cpython/3.14.10+20261110` by `infra/terraform/user_data.sh` at first boot. `release.sh`
built each release's venv with `KV_PYTHON` from `/etc/kalavigyan/box.env`, a file only that first
boot writes, so a new interpreter meant rebuilding the box.

CPython 3.15.2 is in `actions/setup-python` and in python-build-standalone 20261110
(`cpython-3.15.2+20261110-x86_64-unknown-linux-gnu-install_only.tar.gz`, 83,276,502 bytes, sha256
`182e7adf7e4f0e32dafac5143f00d466afd20eef45918ea170f78884e503ac18` in that release's `SHA256SUMS`).
Every package in `backend/uv.lock` has a wheel for it on x86_64 Linux (cp315, abi3 or pure Python),
so the lock resolves from wheels alone, with the same versions.

The geo ETL is the exception. It needs `exactextract`, whose newest release, 0.3.0, publishes
wheels for cp39 to cp314 and none for cp315 (https://pypi.org/project/exactextract/0.3.0/#files,
read 2026-11-21). Building it from source would need GEOS and a C++ toolchain on every runner that
computes district statistics.

What's New in Python 3.15 removes `ctypes.SetPointerType`, `glob.glob0` and `glob1`,
`http.server.CGIHTTPRequestHandler`, the loaders' `load_module`, the `package` argument of
`importlib.resources.files`, `PurePath.is_reserved`, `platform.java_ver`, the `sre_*` modules,
`sysconfig.is_python_build(check_home)`, `CodeType.co_lnotab`, `typing.no_type_check_decorator`,
keyword `NamedTuple` and fieldless `TypedDict` calls, the `wave` markers and
`zipimporter.load_module`, and stops setting `__cached__`. The backend, the tools and the craft ETL
use none of them, nor any API it deprecates or schedules for removal. Of the changed behaviours,
UTF-8 mode by default changes nothing on Linux, where CI and the box already read UTF-8; the one
`strptime` format has a year; both `urlsafe_b64decode` callers pad their input, which keeps their
results the same now that padding is optional, and a `+` or `/` in it still decodes as before, with
a warning instead of silence; no `argparse` option pairs a short flag with a single-dash long one;
and `sqlite3` is not used. `re.match` is soft deprecated in favour of `re.prefixmatch`, with no
warning and no removal planned, so its call sites stay and the code still runs on the 3.14
interpreters that remain: the development machine's venv and every release built before this one.

## Decision

1. **The projects.** `backend/pyproject.toml` and `etl/crafts/pyproject.toml` require
   `>=3.15`, and ruff targets `py315`; ruff 0.17.6 knows the target and raises no finding under it.
   `tools/pyproject.toml` declares no Python and extends the backend's ruff settings.
   `backend/uv.lock` is locked for 3.15: the same versions, with the cp314 wheels and a marker that
   only applied below 3.15 dropped.
2. **CI.** Backend checks, Hygiene, Open data release, Web fonts and Craft data set Python 3.15.
   Geo ETL stays on 3.14 with `etl/geo/pyproject.toml`, and the two move together once
   `exactextract` publishes a cp315 wheel. The Postgres service image does not change.
3. **The interpreter is a release input.** `infra/deploy/python.pin` names the version, the
   python-build-standalone build, the `install_only` address for `x86_64-unknown-linux-gnu` and the
   sha256 the build's `SHA256SUMS` gives it. `release.sh` reads it from the release's own tarball
   and refuses a version, build, address or checksum of the wrong form. Before it builds a release,
   it installs that CPython into `/opt/cpython/<version>+<build>` unless the directory exists, as
   `user_data.sh` does: downloaded over https only, the checksum verified before unpacking,
   unpacked into `/opt/cpython/.incoming.*`, byte-compiled, owned by root with no group or other
   write, and moved into place in one rename. It then checks that the interpreter imports `ssl`,
   `sqlite3` and `venv` and reports the pinned version, builds the venv with it and checks that the
   venv reports the same version. `KV_PYTHON` is no longer read.
4. **Nothing is removed.** No release deletes an interpreter, so every kept release's venv still
   finds the one it was built with.
5. **A rebuilt box.** `user_data.sh` installs the same pinned build at first boot and writes it
   to `box.env` as before.
6. **One minor, checked.** A backend test checks that the pin, `user_data.sh`, the CI workflows,
   `requires-python`, ruff's target and the lock name the same minor version. It also checks that
   the release installs the interpreter by the same steps as the first boot, and that the geo ETL's
   workflow and project agree.

## How the box moves

The first release after this change downloads CPython 3.15.2 and installs it into
`/opt/cpython/3.15.2+20261110` beside `3.14.10+20261110`. It builds the new release's venv on it,
and `blue_green.sh release` starts it in the idle slot, checks `/health` and switches nginx as it
always does. The box itself is not rebuilt, and the live slot is not touched until the switch.
Before this change shipped, one SSM command fetched the pinned tarball into a scratch directory
under `/tmp`, matched its checksum and ran `CPython 3.15.2 OpenSSL 3.5.9` from it on the box, then
removed the directory.

## How it rolls back

- **At once.** `sudo kv-blue-green rollback` starts the previous slot, whose release and 3.14 venv
  are untouched.
- **For new releases.** Revert `python.pin` to 3.14.10 with its checksum, `requires-python` and
  `backend/uv.lock` together, and deploy. The release finds `/opt/cpython/3.14.10+20261110`
  installed and builds on it.
- **No migration.** This change adds no migration, so a rollback needs no downgrade.

## Consequences

- A later interpreter moves by changing `python.pin`, `requires-python`, the lock and the CI
  versions in one change, shipped by an ordinary release, with no box rebuild.
- Interpreters accumulate in `/opt/cpython`. An operator may remove one by hand once
  `readlink -f /opt/kalavigyan/releases/*/backend/.venv/bin/python` shows that no kept release uses
  it.
- The geo ETL runs on a different minor from the rest until `exactextract` publishes a cp315 wheel.
  Its results are files and rows that the backend reads, so the two never share a process.
